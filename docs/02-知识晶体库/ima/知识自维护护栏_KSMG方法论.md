# 知识自维护护栏（KSMG）方法论

**文档编号**: MTH-2026-003
**日期**: 2026-08-10
**来源**: ① ima 记忆系统写入纪律（前缀规范/不推断）的实践提炼 ② OpenWiki 自指涉循环缺护栏的批判 ③ 四源管线质量门/版本链的既有实践
**定位**: 适用于任何"Agent 自维护知识"系统的通用护栏框架（记忆、知识库、文档系统、标注体系）

---

## 一、为什么需要护栏：自指涉循环的三重风险

OpenWiki 的"自指涉循环"（Agent 修改自己的 AGENTS.md）暴露了知识自维护系统的共性风险——**Agent 既是知识的消费者，又是知识的维护者，两者叠加会产生三种系统性问题**：

| 风险 | 机制 | 后果 | 例子 |
|------|------|------|------|
| **R1 自我强化偏差** | Agent 生成的知识反哺 Agent 输入 → 错误被下一轮生成引用 | hallucination 固化，越维护越偏离 | Wiki 页 A 有错 → Agent 生成页 B 引用 A → B 错 → 循环放大 |
| **R2 知识漂移** | 持续维护中，知识逐渐偏离源头（源数据已变，知识未更新） | 知识"看起来新鲜"，实际过时 | Git Diff 只重生成"变化页"，语义过时的旧页被漏掉 |
| **R3 无验证写入** | 维护者=写作者=验证者，缺乏独立校验 | 错误知识以"权威"形态沉淀 | 全 0 权重树文件被当正常数据继续诊断 |
| **R4 接口漂移** | 知识系统的多个模块分别演进，共享接口未联调 | 模块组合时崩溃或静默错位 | quality_gate 导入 `validate_tree_file` 不存在（ImportError）——两文件分别更新、缺联调验证（2026-08-10 生产侧实证） |

**核心洞察**：护栏不是限制 Agent 的能力，而是**切断 R1-R4 的传播路径**——让"维护"与"验证"分离，让"写入"有明确语义，让"来源"可追溯，让"接口"有契约。

## 二、护栏六层模型（KSMG）

```
┌─────────────────────────────────────────────────────────┐
│                   知识自维护系统                           │
│                                                         │
│  G1 来源护栏 ── 只记事实，不记推断（切断 R1 的输入）           │
│  G2 格式护栏 ── 结构强制，路由明确（保证可机读可审计）          │
│  G3 变更护栏 ── 更新/删除语义显式（切断 R2 的漂移）            │
│  G4 审计护栏 ── 版本戳 + 变更日志（保证可追溯可回滚）           │
│  G5 验证护栏 ── 写入即验证（切断 R3 的沉淀）                  │
│  G6 契约护栏 ── 接口契约 + 联调冒烟（切断 R4 的错位）          │
│                                                         │
│  输入（源数据/事实）→ [G1] → [G2] → [G3] → 知识库 → [G5] 校验 │
│                              ↑                    │        │
│                              └──── [G4] 全程审计 ──┘        │
│  模块间（采集→诊断→导出）──────── [G6] 契约+冒烟 ──────────   │
└─────────────────────────────────────────────────────────┘
```

| 层 | 名称 | 作用 | 核心机制 |
|----|------|------|----------|
| **G1** | 来源护栏 | 切断"错误输入" | 只记事实不记推断；锚定当前；不补填/不回填 |
| **G2** | 格式护栏 | 保证可机读 | 操作前缀规范；按主题路由分文件；原子事实；去人称 |
| **G3** | 变更护栏 | 切断知识漂移 | 更新 vs 删除显式区分；覆盖策略；四同步 |
| **G4** | 审计护栏 | 保证可追溯 | 版本戳（provenance）；变更日志；run_id |
| **G5** | 验证护栏 | 切断错误沉淀 | 写入即校验；质量门；失败显式化；外部对齐 |
| **G6** | 契约护栏 | 切断接口错位 | 接口契约文档；import 冒烟测试；结果格式契约；联调测试 |

## 三、各护栏详细设计

### G1 来源护栏：只记事实，不记推断

**原则**：知识库只存放"源明确陈述的事实"，推断/建议/猜测永远不写入——推断留在对话，事实才入知识。

| 规则 | 说明 | ✅ 例 | ❌ 反例 |
|------|------|-------|--------|
| R1-1 锚定当前查询 | 只记录当前轮次明确陈述的，不追溯历史轮次"补填" | 用户说"选方案 A"→ 记"用户确认方案 A" | 用户本轮说"继续"，回填上上轮的决策 |
| R1-2 不推断不补填 | 不写"用户可能想要 X"，不记录第三方只言片语 | 用户明确说"用 hf-mirror"→ 记 | 用户提到某工具一句 → 记"用户使用 X 工具" |
| R1-3 原子事实 | 一条 entry 一个事实 | "C_k 未激活（四源全 0）" | "C_k 未激活且 K_y 也变了且……"（多事实混写） |
| R1-4 场景保留 | 用户明确命名的场景保留，人称前缀删除 | "汇报给主管时，用 X 格式" | "和用户说话时用 X"（人称为默认主语） |
| R1-5 状态标记 | 知识带 status（稳定/待验证/已废弃） | "逆生回流假设：3/3，待 P1-3 验证" | 假设与结论混写无状态 |

**切断 R1 的关键**：推断不进知识库 → 下一轮 Agent 引用的都是"事实"，自我强化偏差失去"错误种子"。

### G2 格式护栏：结构强制

**原则**：所有写入必须满足可机读格式——无格式不写入。

| 规则 | 说明 |
|------|------|
| R2-1 操作前缀 | 写入必须带显式操作：`增加/更新` / `删除` / `清空`——机器可识别意图 |
| R2-2 主题路由 | 按知识主题分文件（行为规则/用户档案/长期记忆/工具经验），一条事实只属一个文件 |
| R2-3 原子条目 | 同文件多事实 → 各包独立 entry，不混写 |
| R2-4 去人称噪声 | 默认主语是系统/用户，不加"当与用户交流时"类前缀 |

### G3 变更护栏：更新语义显式

**原则**：更新与删除是不同语义的操作，必须显式声明——防止"覆盖旧知识"与"新增知识"混淆导致漂移。

| 规则 | 说明 | 对应实践 |
|------|------|----------|
| R3-1 更新显式覆盖 | 知识变化 → `更新`（覆盖旧值），不叠加不并存 | 记忆覆盖旧版本 |
| R3-2 删除显式声明 | 废弃知识 → `删除`，不留"已失效但仍在"的僵尸条目 | "不再需要记 X" → 删除 |
| R3-3 四同步 | 知识变更时，所有引用方同步更新（canonical/树文件/诊断/版本号） | 标注治理三次分裂教训 |
| R3-4 版本戳 | 每次变更打版本号，旧版本归档不静默消失 | schema_version / coeff_version |

**切断 R2 的关键**：知识漂移源于"更新了源头但没更新知识"——R3-3 四同步 + R3-4 版本戳强制"一处变更，处处同步"。

### G4 审计护栏：可追溯可回滚

**原则**：知识库的每一次变更都可以回答"谁、何时、为什么、从什么变成什么"。

| 规则 | 说明 |
|------|------|
| R4-1 provenance 版本链 | 数据/知识带完整来源链（采集/标注/系数/引擎版本） |
| R4-2 变更日志 | 运行日志（run_id）、采集日志、仲裁文档——全链可审计 |
| R4-3 回滚路径 | 旧版本备份（engine_v2_series_OLD.json）、Git 回滚 |

### G5 验证护栏：写入即验证

**原则**：知识进入库之前必须过门——**没有验证的知识不沉淀**。

| 规则 | 说明 | 对应实践 |
|------|------|----------|
| R5-1 质量门 | 写入前跑校验（schema/合法性/量级/一致性） | 质量门七检查点 |
| R5-2 失败显式化 | 采集/生成失败必须显式标记，不产出"伪正常"数据 | 全 0 树文件识别 |
| R5-3 外部对齐 | 关键知识用外部参照二次确认 | 标注仲裁人工核验（S2/Scholar） |
| R5-4 置信度标记 | 无法验证的知识标记"待验证"，不冒充结论 | "待完整月复验" |

**切断 R3 的关键**：错误知识无法通过质量门 → 不会以"权威"形态沉淀。

### G6 契约护栏：接口契约 + 联调冒烟

**原则**：知识系统是多模块协作（采集→诊断→导出→展示），**模块间接口必须有契约，组合后必须冒烟**——防止"分别演进、静默错位"。

**实证教训（2026-08-10 生产侧）**：quality_gate.py 导入 `validate_tree_file`/`VALID_WUXING`，但 data_validator.py 实际提供 `validate_tree`/`WUXING_ORDER`，且检查结果格式期望（字符串）与实际（dict）不匹配——**两模块分别更新、缺联调，运行即崩**。

| 规则 | 说明 | 对应实践 |
|------|------|----------|
| R6-1 接口契约先行 | 模块共享接口先写契约文档（函数签名/返回格式/常量名），双方按契约实现 | IF-2026-006（晶体Schema与PhaseB_接口契约） |
| R6-2 import 冒烟测试 | 每个模块入口必须可导入；组合模块（A import B）必须有 import 测试 | quality_gate ImportError 教训——补 import 冒烟入 tests/ |
| R6-3 结果格式契约 | 返回值格式契约化（dict 结构/状态枚举），不靠 startswith/魔法字符串判断 | 检查点结果 `{"status","message"}` 而非字符串前缀 |
| R6-4 联调测试 | 模块组合后跑全链路（质量门→诊断→导出），验证契约真实生效 | verify_crystal_link.py（7/7） |

**切断 R4 的关键**：接口有契约（R6-1）→ 实现不错位；组合有冒烟（R6-2/6-4）→ 错位立即暴露，不静默进入生产。

## 四、与 OpenWiki 缺护栏点的对照

| OpenWiki 缺失 | KSMG 对应层 | 补法 |
|---------------|-------------|------|
| 自指涉循环无护栏（Agent 改自己的 AGENTS.md 无独立校验） | **G1 + G5** | 写入只记"事实/变更"，且写入后过验证门（schema/一致性） |
| 无自动验证层（靠人审 + 回滚） | **G5** | 质量门前置：生成内容先过校验再注入 |
| Git Diff 增量漏"未变化但过时"的知识 | **G3 + G1-5** | 更新语义显式（区分"内容变"与"知识过时"）+ 知识带 status/时效 |
| "文档不是人写的"可信度悬空 | **G1 + G4** | 来源标记（谁生成/来自哪）+ provenance 全链 |

## 五、应用矩阵：KSMG 在你三大体系中的落地

| 体系 | G1 来源 | G2 格式 | G3 变更 | G4 审计 | G5 验证 | G6 契约 |
|------|---------|---------|---------|---------|---------|---------|
| **ima 记忆系统** | ✅ 已实践（不推断/锚定当前） | ✅ 已实践（前缀/路由/原子） | ✅ 已实践（增/删/清语义） | ⚠️ 部分（无显式版本戳） | ⚠️ 人工（无自动校验） | — |
| **四源管线** | ✅ provenance 来源链 | ✅ 树文件 schema | ✅ 四同步 + 版本戳 | ✅ run_id/备份 | ✅ 质量门七检查点 | ⚠️ 契约有（IF-2026-006）但 **import 冒烟缺失**（quality_gate 实证） |
| **标注治理** | ✅ 仲裁依据记录 | ✅ canonical 统一 | ✅ 三处同步 + 版本化 | ✅ 仲裁文档 | ⚠️ 人工核验（S2 工具化） | — |
| **未来 OKF 知识库** | status/sources（OKF 原生） | Markdown+YAML | 版本化目录 | Git 历史 | **你的质量门方法论可反向输出** | 契约参考 IF-2026-006 |

**关键发现**：ima 记忆系统天然实现了 G1/G2/G3（写入纪律），四源管线实现了 G4/G5（质量门/版本链）——**两套体系合起来就是完整的 KSMG**。缺的三块：
1. 记忆系统无自动验证（G5 人工）——可加"写入后 diff 检查"
2. 记忆系统无显式版本戳（G4 部分）——可加"记忆变更日志"
3. **四源管线缺 G6 import 冒烟**——quality_gate 接口错位实证：契约文档存在（IF-2026-006）但组合模块未冒烟，错位静默进入生产

## 六、KSMG 检验清单（反例驱动的护栏自检）

每次"Agent 自维护知识"后，用 6 个问题自检：

| # | 问题 | 对应护栏 | 失败信号 |
|---|------|----------|----------|
| 1 | 这条知识是**事实**还是**推断**？ | G1 | 有"可能/应该/也许"→ 推断，未过 G1 |
| 2 | 它是否带**操作语义**（新增/更新/删除）？ | G2/G3 | 无前缀的裸写入 |
| 3 | 变更是否**同步到所有引用方**？ | G3 | canonical 改了树文件没改 |
| 4 | 能否回答"**从什么变成什么**"？ | G4 | 无版本戳无备份 |
| 5 | 写入前是否**过了验证门**？ | G5 | 全 0 数据直接进诊断 |
| 6 | 模块接口是否**契约化且可导入**？ | G6 | import 报错 / 结果格式靠字符串猜测 |

## 七、一句话定位

> **KSMG 六层护栏（来源/格式/变更/审计/验证/契约）是把"Agent 自维护知识"从浪漫叙事变成可信工程的方法论：来源护栏切断错误种子（只记事实），格式护栏保证可机读（前缀路由），变更护栏阻断知识漂移（四同步），审计护栏确保可回滚（版本链），验证护栏拒绝错误沉淀（质量门），契约护栏防止接口错位（契约+冒烟）。OpenWiki 缺的正是这五层（G1-G5），而生产侧 quality_gate 事件补上了第六层（G6）的实证——**知识可以自维护，但护栏让自维护不等于自欺；接口有契约，错位才不等于事故。**」

*待办: ① 记忆系统加写入后校验（G5 自动化）② 记忆变更日志（G4 补全）③ 四源管线补 G6 import 冒烟测试（quality_gate 修复后入 tests/）④ 可选：输出为 Skill 供跨会话复用*
